## Verdict

The M0 scaffold is well organised and the x86 path is green: `fmt`, `clippy -D warnings`,
`cargo test --workspace` and the `--features onnx` tests all pass, and
`cargo run -p edge-vision -- config/x86-dev.toml --frames 30` processes 30 frames.

But there are **four things that are actually broken**, and several places where
`design.md` claims behaviour the code does not implement. The biggest risk is that the
design body was not updated after the 2026-10-23 revision: an agent reading the body will
implement **direct libargus + pitch-linear + "Nano never CPU"**, while the revision says
**GStreamer hybrid + block-linear NVMM + Nano CPU encode opt-in**. Those are not small
differences; they change the capture API, the buffer types, the M1 scope and the Nano
product story.

The performance targets in `design.md` are also not achievable with the current defaults
(see P1-10): `queue_depth = 4` plus an `appsink` queue of 6 can add ~10 frame periods
(≈330 ms at 30 fps) before a frame reaches the encoder.

## P0 — fix before the next milestone

### P0-1. A stage error deadlocks the process when the source is unbounded

**Where:** [`crates/pipeline/src/lib.rs:204`](crates/pipeline/src/lib.rs#L204) (receive loop),
[`crates/pipeline/src/lib.rs:216`](crates/pipeline/src/lib.rs#L216) (`capture.join()`),
[`crates/pipeline/src/lib.rs:177`](crates/pipeline/src/lib.rs#L177) (capture loop).

**What happens:** `run()` owns `rx` for the whole function. If `process_one()` returns an
error (sink write fails, engine fails, overlay fails), the loop breaks and `run()` calls
`capture.join()`. The capture thread has no way to see that the consumer is gone: the
channel's `Sender::send` never fails, the receiver is still alive, and the capture loop
only stops on `source.frames`, `max_frames`, or end-of-stream. An infinite source
(the production case: `config/orin-nx-yolo.toml` has no `frames`) therefore never exits,
and `join()` blocks forever.

**Reproduced:** a sink that returns an error on the third `push_meta`; `pipeline.run(None)`
never returned (test killed after 20 s). The same applies to any RTSP sink that returns an
error.

**Why it matters:** the design promises clean shutdown and error handling; a recoverable
sink error becomes a hung process that stops the camera and needs a watchdog restart.

**Suggested fix:**
- Add a shared `AtomicBool` stop flag (or `impl Drop for Receiver` that marks the channel
  closed and notifies, plus make `Sender::send` return `Err` when closed). The capture
  thread checks the flag each iteration, calls `source.stop()`, and returns.
- Drop/close the receiver **before** `join`, so the sender sees the disconnect.
- Add a regression test: sink errors at frame 3, source unbounded, `run()` returns `Err`
  within a bounded time.

### P0-2. `Ok(None)` conflates "timeout" with "end of stream"; an undersized pool silently truncates the run

**Where:** [`crates/core/src/stage.rs:52`](crates/core/src/stage.rs#L52),
[`crates/platform-sim/src/lib.rs:156`](crates/platform-sim/src/lib.rs#L156),
[`crates/pipeline/src/lib.rs:186`](crates/pipeline/src/lib.rs#L186),
[`crates/core/src/config.rs:226`](crates/core/src/config.rs#L226).

**What happens:** `FrameSource::next_frame` returns `Result<Option<HwFrame>>`; the doc says
`Ok(None)` means "timeout or end of stream". The pipeline treats `None` as EOS and breaks.
The sim source returns `None` both for real EOF and for "pool exhausted after the timeout".
Validation only requires `pool_size >= 3`, so a perfectly legal config can have a pool
smaller than `queue_depth + frames-in-processing`.

**Reproduced:** `pool_size = 3`, `queue_depth = 4`, 30 frames requested, sink sleeping
200 ms/frame:
```
captured=4 dropped=0 processed=4 ...
```
The run exits "successfully" after 4 frames. With the default `pool_size = 6`,
`queue_depth = 4`, the channel evicts and the run continues (`captured=30 dropped=25
processed=5`), so the truncation is configuration-dependent — but any genuine camera
hiccup/timeout still looks like EOS and stops the pipeline.

**Why it matters:** one slow sink or a transient buffer shortage ends the stream with a
success status and no drop count. This directly contradicts the design's "pool exhaustion
drops the oldest frame rather than blocking the sensor" and makes `frames_dropped`
unreliable.

**Suggested fix:**
- Replace the sentinel with an explicit enum:
  `enum FramePoll { Frame(HwFrame), Timeout, EndOfStream }`.
  The pipeline continues on `Timeout` (increment a `capture_timeouts`/`frames_dropped` counter)
  and only breaks on `EndOfStream`.
- Validate `pool_size >= queue_depth + 3` (capture + queue + in-flight processing), or
  compute a recommended minimum and print it in `buffer_budget()`.
- Add a test that runs with a slow sink and an undersized pool and asserts either
  "continues" or "clear error", never "silent EOS".

### P0-3. Revision 3 (Orin Nano CPU encode opt-in) is unreachable in the current code

**Where:** [`crates/pipeline/src/lib.rs:88`](crates/pipeline/src/lib.rs#L88),
[`crates/core/src/config.rs:254`](crates/core/src/config.rs#L254),
[`crates/platform-jetson/src/probe.rs:68`](crates/platform-jetson/src/probe.rs#L68),
[`apps/edge-vision/src/main.rs:77`](apps/edge-vision/src/main.rs#L77),
[`apps/edge-vision/Cargo.toml:12`](apps/edge-vision/Cargo.toml#L12).

**What happens:** `Pipeline::build` refuses any encoder when `!caps.has_hw_encoder`,
*before* calling `platform.encoder()`. So `zero_copy = "relaxed"` + `encoder.hardware =
false` on a Nano still fails with "no hardware encoder". On a platform that does advertise
a HW encoder (Orin NX), `encoder.hardware = false` is never checked by the builder or by
`EncoderKind`; `choose_encoder()` is only called from its own unit tests. The app has no
`platform-jetson` dependency at all (`jetson = []` is an empty feature), so
`config/orin-nx-yolo.toml` always bails in `main.rs`.

**Why it matters:** the revision's decision 3 is a product decision (Nano can stream video
as an explicit opt-in). Right now the code cannot express it, and a reader of the design
will assume it exists.

**Suggested fix:**
- Add `PlatformCaps::cpu_encode: bool` (or an `EncodePath` enum) and allow an encoder when
  `caps.has_hw_encoder` **or** (`zero_copy == Relaxed && caps.cpu_encode && !encoder.hardware`).
- Have `Platform::encoder` return the chosen kind (or have the builder call
  `choose_encoder()`), and validate the returned kind against `encoder.hardware` and
  `zero_copy`.
- Wire `jetson = ["dep:platform-jetson"]` and construct `JetsonPlatform` when the feature
  is on; otherwise keep the clear error.
- Test both: strict+Nano refuses; relaxed+Nano+`hardware=false` returns a CPU encoder;
  relaxed+NX+`hardware=true` returns NVENC.

## P1 — zero-copy and HAL: the types don't enforce the contract

### P1-6. `EncodedPacket` copies every encoded frame; `MultiSink` copies it again

**Where:** [`crates/core/src/stage.rs:42`](crates/core/src/stage.rs#L42),
[`crates/sinks/src/lib.rs:102`](crates/sinks/src/lib.rs#L102).

`EncodedPacket { data: Vec<u8> }` means the encoder must allocate/copy the bitstream into a
`Vec` per packet. `MultiSink::push_video` clones the packet for every child except the last,
so a 2-sink fan-out makes a second full copy. The design says the bitstream is "wrapped from
the V4L2 mmap, no copy" and that steady-state allocations are 0. Encoded bytes are small
(~33 KB/frame at 8 Mbps), so this is not a pixel copy — but it breaks the stated
zero-allocation/zero-copy contract and the multi-sink path is O(packet size).

**Suggested fix:** make the payload a shared handle (`Arc<dyn ByteBuffer>` / `bytes::Bytes`
/ `GstSample` behind a feature) and pass it by cheap clone; let the encoder hand out a
packet that owns the buffer/mmap until the sink drops it.

### P1-7. Layout and plane information are missing, and the builder hardcodes pitch-linear

**Where:** [`crates/pipeline/src/lib.rs:79`](crates/pipeline/src/lib.rs#L79),
[`crates/core/src/frame.rs:58`](crates/core/src/frame.rs#L58),
[`crates/core/src/frame.rs:95`](crates/core/src/frame.rs#L95),
[`crates/core/src/frame.rs:100`](crates/core/src/frame.rs#L100).

`Pipeline::build` builds `PreConfig { layout: Layout::PitchLinear }` unconditionally, while
`FrameMeta.layout` is per-frame and `nvarguscamerasrc` produces block-linear NV12. The
preprocessor can read `frame.meta.layout`, but the config it receives says pitch-linear.
There is also no pitch/stride/plane-offset in `FrameMeta`, and `HwBuffer::dmabuf_fd()`
returns a single `RawFd` for a buffer that may have multiple planes (or a single fd with
plane offsets — the API doesn't say which). `map_cpu()` returns a flat `&[u8]`, which is
not a row-major image for block-linear NVMM.

**Why it matters:** this is exactly the class of bug the design says it prevents ("strict
domain matching … block-linear vs pitch-linear"). Right now there is nothing to match
against except the global `PlatformCaps.frame_memory`.

**Suggested fix:** add a plane/layout descriptor to `FrameMeta` (pitch, plane offsets,
color space/range), make `FrameSource` declare its output layout, derive `PreConfig.layout`
from it, and have the builder reject a mismatch. For fds, either expose
`fds() -> &[RawFd]` + offsets, or document and enforce "one contiguous NV12 allocation".
Replace `CpuMapping<'_> { data: &[u8] }` with a plane-aware mapping, or remove `map_cpu`
from the core until it can represent block-linear memory correctly.

### P1-8. `appsink drop=false` + `max-buffers=6` adds latency and blocks Argus; `appsrc` is unbounded

**Where:** [`crates/platform-jetson/src/launch.rs:32`](crates/platform-jetson/src/launch.rs#L32),
[`crates/platform-jetson/src/launch.rs:56`](crates/platform-jetson/src/launch.rs#L56).

`appsink … max-buffers={pool_size} drop=false sync=false`:
with `drop=false`, the appsink queue is bounded by `max-buffers` and **blocks upstream**
when full; it does not drop. A full queue is up to 6 frames = 200 ms at 30 fps, before the
Rust `queue_depth = 4` channel (another 133 ms) and processing. That makes the
`< 100 ms p95` target impossible with the shipping defaults. The design's "drop oldest"
happens in the Rust channel, not in the appsink.

`appsrc … is-live=true format=time` has no `block`/`max-bytes`/`max-buffers`; if NVENC is
slower than capture, appsrc can grow without bound (or block with default semantics —
either way it should be explicit).

**Suggested fix:** use `drop=true` with a small `max-buffers` (1–2) and keep the
drop-oldest policy in Rust; add `max-bytes`/`block=true` (or a leaky queue) on the encoder
appsrc. Then measure end-to-end p95 with a timestamped frame, not by eye.

### P1-9. "Same dmabuf into NVENC" is unproven, and `nvmmalloc` is the wrong name

**Where:** [`design.md:14`](design.md#L14),
[`crates/platform-jetson/src/launch.rs:11`](crates/platform-jetson/src/launch.rs#L11).

The design correctly says the `appsrc → nvv4l2h26xenc` zero-copy path needs an NVMM
`GstAllocator` and that JetPack 7 validation is ours. Two corrections:

- The reference project documents `GstNvmmAllocator`, `GstNvmmBufferPool`, `nvmmconvert`,
  `nvmmsink` and `nvmmappsrc`; I could not find an element named `nvmmalloc` in it
  ([gst-nvmm-cpp write-up](https://pavelguzenfeld.com/posts/gst-nvmm-cpp-zero-copy-video-jetson/)).
  Check the actual element/allocator name before writing it into the launch-string contract.
- Even with an allocator, `nvv4l2h264enc` may still copy into its own V4L2 buffers on some
  JetPack versions. Do not claim "zero-copy from sensor to encoder" until Nsight Systems
  shows no `DtoD`/`HtoD` and `tegrastats` EMC load matches one write per frame on the
  actual board. The design already lists this as a gate; make M1 exit depend on it.

Also, the design's "the only copy no user-space design can avoid is the socket send" is
too strong: RTP payloading (`rtph264pay`) creates new buffers/packets; budget that bitstream
copy explicitly.

### P1-10. The HAL is still Jetson-shaped: closed enums, one domain, no device/precision

**Where:** [`crates/core/src/frame.rs:12`](crates/core/src/frame.rs#L12) (`FrameMemory`),
[`crates/core/src/frame.rs:29`](crates/core/src/frame.rs#L29) (`Layout`),
[`crates/core/src/frame.rs:44`](crates/core/src/frame.rs#L44) (`PixelFormat`),
[`crates/core/src/config.rs:63`](crates/core/src/config.rs#L63) (`ModelConfig`),
[`crates/core/src/stage.rs:25`](crates/core/src/stage.rs#L25) (`GpuStream`).

`FrameMemory` has exactly `Nvmm | DmaBuf`; Ambarella's IAV/DSP shared memory (listed in the
porting table) has no variant, so adding it forces a core change — violating goal 2.
`Layout` is `PitchLinear | BlockLinear`; `PixelFormat` is `Nv12` only. `ModelConfig` has no
`precision` (FP16/INT8) or `device` (GPU/DLA core), and `PlatformCaps.accelerators` is a
bag of strings; `GpuStream` is only a `u32` id. The config-driven goal says "one TOML picks
… encoder" but there is no way to select INT8 or DLA from TOML, and `build-engine.sh` always
passes `--fp16` (no `--int8`, no `--useDLACore`).

**Suggested fix:** make the memory domain an opaque backend-defined tag
(`Domain(&'static str)` / UUID) and keep only the properties the pipeline needs
(dmabuf-importable, host-visible, etc.); add `model.precision` and `model.device`, validate
them against `PlatformCaps`, and extend `build-engine.sh`/the engine loader accordingly.
`GpuStream` can stay an id, but document that the backend maps it to a `cudaStream_t`/DLA
context.

### P1-11. `Tensor::as_f32_slice_mut` silently fails if the engine shares an `Arc`

**Where:** [`crates/core/src/tensor.rs:64`](crates/core/src/tensor.rs#L64).

`Arc::get_mut(&mut self.buf)?` returns `None` as soon as any other `Arc` clone exists. A
TensorRT backend may keep an `Arc` to its input binding for `setTensorAddress` /
`enqueueV3`; then a preprocessor calling `as_f32_slice_mut()` gets `None` and the
preprocessor fails (or a host backend silently skips). The design's "preprocessor writes
into the engine's input binding" assumes unique ownership.

**Suggested fix:** give `TensorBuffer` interior mutability (`Mutex`/`UnsafeCell` guarded in
the backend) or pass `&mut dyn TensorBuffer` from the engine rather than an `Arc` clone;
add a conformance test where the engine holds a second reference and the preprocessor still
writes.

### P1-12. NMS and post-processing allocate per frame; `PostProcessor::decode` is `&self`

**Where:** [`crates/core/src/stage.rs:74`](crates/core/src/stage.rs#L74),
[`crates/postproc/src/nms.rs:31`](crates/postproc/src/nms.rs#L31).

`decode(&self, …)` prevents a decoder from reusing scratch buffers; `nms_inner` does
`vec![true; detections.len()]` for every frame. The design says "steady-state allocations
in hot loop = 0" and "a counting global allocator in tests fails the build". Neither the
allocator test nor the zero-allocation path exists. Also, `YoloPostProcessor` runs NMS on
all candidates above threshold with no pre-NMS top-k cap, so a crowded scene can make
post-processing O(n²) (8400 candidates); Ultralytics-style decoders cap before NMS.

**Suggested fix:** `decode(&mut self, …)` with reusable `Vec<bool>`/candidate scratch and a
`max_det`/`max_nms` cap; add a `#[global_allocator]` counting test around a 100-frame loop
and assert 0 steady-state allocations (excluding startup).

### P1-13. The fd assertion is compiled out in release; "same fd" is not enforced

**Where:** [`crates/pipeline/src/lib.rs:266`](crates/pipeline/src/lib.rs#L266).

`debug_assert_eq!(frame.meta.dmabuf_fd, frame.buf.dmabuf_fd())` disappears in release,
which is where the product runs. The encoder receives the whole `HwFrame` and can ignore
the fd entirely. If the design wants "the encoder asserts it is encoding that same fd",
make it a typed error (or a checked wrapper that returns the fd/plane handle to the
encoder), not a debug assert. Also, `HwFrame.meta` is public and mutable, so any stage can
rewrite the fd; making `meta` private with an accessor would make the contract structural.

## P2 — design/doc, metrics, config and tests

### P2-14. The performance targets are not measurable with the current code

- **Latency:** the default `queue_depth = 4` + appsink queue 6 can hold ~10 frames
  (≈330 ms at 30 fps) before processing; `< 100 ms p95` needs a much smaller queue and/or a
  "drop frames older than X ms" policy based on `FrameMeta.pts`.
- **CPU:** `< 25% of one core` conflicts with the revision's Nano CPU path (~1.1 cores) —
  qualify it: strict profiles only, or update the target table for the relaxed profile.
- **Allocations:** 0 is not tested and is false today (packet `Vec`, NMS `keep`, sim
  file-read `Vec`).
- **2 cameras:** there is one `Pipeline` for one source; no multi-camera orchestration.

There is no p95/latency histogram, no queue-depth/GPU/DLA/EMC/RSS metric, no `tracing`
spans and no Prometheus HTTP exporter. `PipelineMetrics` has cumulative totals only;
`frames_dropped` only counts channel evictions. The design's "what to measure from day one"
list is largely unimplemented.

### P2-15. Config fields that do nothing (or silently mean something else)

- `stream.rtsp_port` is never read; there is no RTSP/WebRTC sink.
- `stream.metadata_only` is validated for conflict but the builder derives `metadata_only`
  from `encoder.is_none()`; `metadata_only = false` + `encoder.enabled = false` silently
  runs metadata-only instead of erroring.
- `zero_copy` only gates `encoder.hardware = false`; it does not gate pixel copies or
  stage domains, so a backend that copies pixels still passes "strict".
- `encoder.hardware` is ignored by the platform on an NX (it returns a HW encoder either
  way).
- `model.path` on sim without `--features onnx` errors clearly (good), but
  `config/orin-nx-yolo.toml` can never run because the app rejects `platform = "jetson"`.

Decide per field: implement it, or remove it until M1, or fail fast when it is set but
unsupported.

### P2-16. README/design status overclaims

- [`README.md:17`](README.md#L17): CI aarch64 cross-build is `[x]` but fails (P0-4).
- [`README.md:22`](README.md#L22): "YOLOv8/v11 decoder … verified end to end through the
  pipeline" — there is no end-to-end YOLO test; `yolo-const.onnx` is generated but unused.
  The decoder only has unit tests. Add a `decoder = "yolo"` pipeline test with the fixture,
  or downgrade the claim.
- [`design.md:305`](design.md#L305): the conformance suite is said to check golden-image
  preprocessing and mAP within 1–2 points; [`crates/conformance/src/lib.rs:19`](crates/conformance/src/lib.rs#L19)
  explicitly says those are not covered. Either implement them or change the design.
- [`design.md:331`](design.md#L331): "`map_cpu` counted in metrics; CI fails if called in
  the hot loop" — not implemented.
- [`design.md:90`](design.md#L90): counting allocator test — not implemented.
- [`design.md:340`](design.md#L340): golden-frame tests on `platform-sim` — not implemented
  (there are no golden tests at all).
- [`design.md:52`](design.md#L52): "Orin Nano targets are the same at one camera" — Nano has
  no NVENC; the sentence should be scoped to the strict/CPU-opt-in profiles.

### P2-17. Sim is Linux-only and its "dmabuf" is a regular file

**Where:** [`crates/platform-sim/src/lib.rs:41`](crates/platform-sim/src/lib.rs#L41),
[`crates/platform-sim/src/lib.rs:6`](crates/platform-sim/src/lib.rs#L6).

`/dev/shm` + `std::os::fd` means the "runs on any laptop & CI" claim is false on macOS and
Windows. `SimBuffer::dmabuf_fd()` returns a `/dev/shm` file fd, not a dmabuf; the
conformance suite only checks `fd >= 0` and `meta.fd == buf.fd`, so it cannot catch an
unimportable fd. Pool file names are `edge-vision-sim-{pid}-{i}`; parallel tests in one
process can race on the same path (open/truncate before unlink). Suggest `tempfile`/`memfd`
with a global unique suffix, document Linux-only (or add a Windows fallback), and either use
`udmabuf`/dma-heap in the sim or state clearly that the sim validates traits, not dmabuf
importability.

### P2-18. `build-engine.sh` can return the wrong cached engine

**Where:** [`tools/build-engine.sh:34`](tools/build-engine.sh#L34),
[`tools/build-engine.sh:43`](tools/build-engine.sh#L43).

The cache key is `(model hash, trtexec version)` but the script accepts extra trtexec args.
`tools/build-engine.sh model.onnx --int8` after an FP16 build returns the **FP16 engine**;
same for `--useDLACore=1`, different `--shapes`, etc. Also, TensorRT engines are
device/arch-specific, so an Orin NX engine and an AGX Orin engine with the same TRT version
must not share a cache entry. The version parse uses `trtexec --help`; if that does not print
`TensorRT vX.Y`, the script dies — verify on the target or use `dpkg-query`/`python -c
"import tensorrt"`.
Suggested: include a hash of `"$@"` + GPU/SoC/arch + JetPack release in the key; write the
args to a sidecar; validate with `--loadEngine` before returning.

### P2-19. Design facts/nits to fix while rewriting

- `design.md:81`: "output tensors (~1 MB for a YOLO-class head)" — YOLOv8 640×640 with 80
  classes is `[1,84,8400]` = 2.82 MB in F32 (~1.4 MB in F16). Use the actual model shape.
- `design.md:76` uses 1920×1080 for the buffer budget while the shipping config is
  1440×1080 (IMX296); recompute with the real mode and actual NVMM pitch (1440 may be
  padded to 1536/2048).
- `design.md:70`: "every other hardware buffer is written exactly once" — the capture
  surface is written by the ISP and then by the overlay, and possibly by VIC if a layout
  conversion is needed. Reword.
- `design.md:79`/`270` mix V4L2 M2M mmap and GStreamer appsrc; after the revision it is
  GStreamer. Pick one per milestone.
- `design.md:114`: "static dispatch in the hot path … stages are boxed trait objects" is
  contradictory; boxed trait objects are dynamic dispatch (cheap once per frame, but say
  so).
- `design.md:149`: "every backend must provide a dmabuf fd" vs the porting guide's "expose
  a dmabuf fd if one exists" (Ambarella may not). Decide and enforce.
- `design.md` "Orin Nano CPU encode … 30 fps at ≈1.1 Orin NX cores": NVIDIA's table is
  H.264/1080p30; x265 at 1080p30 on a 6-core Orin Nano is not supported by that data.
  Restrict the claim to H.264 or measure x265 before shipping it in the config.

## Minor / cleanup

- `Core` `Error::Timeout` is unused; `ZeroCopyMode` relaxed has no effect on the pipeline
  beyond the config check.
- `PipelineMetrics::avg` divides by `u32` and saturates above `u32::MAX` frames.
- `buffer_budget()` prints "FP16" even for the sim/ONNX F32 engines, and "bytes x pool"

  width; boxes clipped at the edge can be slightly wrong.

- `main.rs` `--prometheus` prints at the end only; no endpoint. Fine for M0, but the design
  says "exported".
- `README` "M0 scaffold" is accurate apart from the cross-build and YOLO e2e checkboxes.

### What to copy into `design.md`

1. **Environment record** (Compatibility §4) as the M1 exit artifact: module/carrier revision,
   BSP/boot medium, kernel, CUDA/TensorRT, container digest, model hash, power mode, cooling,
   checks run/pending.
2. **Buffer ownership/budget worksheet** (Memory §9): every live allocation with shape/dtype,
   pitch/layout, bytes, owner, consumers, lifetime; this is exactly what P1-7 asks for and
   would have caught the pitch-linear/block-linear mistake.
3. **Queue/freshness policy** (Real-Time §5–6): bounded queue, expire at admission **and**
   consumption, report p95 end-to-end age, not average FPS. This is the missing half of
   P0-2 and the `<100 ms` target.
4. **Camera evidence package** (Camera §10): raw capture + Argus path + dual VC mapping +
   timestamp/exposure sync; use it as the M1 camera gate. The design currently jumps from
   "dual VC IMX296" to "appsink".
5. **Power/thermal statement**: record `nvpmodel` mode, cooling, ambient, clocks and
   `tegrastats` with every performance number; otherwise the target table is not reproducible.
6. **Engine build/validation** (Real-Time §3): `trtexec --skipInference` to build,
   `--loadEngine` to validate, and a cache key that includes args/GPU/arch. Replace the
   fragile `trtexec --help` version parse in `tools/build-engine.sh`.
